# etkn-monitor —— ETKN 监控（v3.18.3）

手机友好的 ETKN（ETK vNext）监控面板：队列规模、入库进度、完成速率与 ETA、分类任务统计、手动链路测速、失败任务重试、手动整理触发、异常媒体明细。

**v2.9.21 变化**（2026-09-29）——修「中转池自检在手机上点不动」（面板走 CDN 超时）：

- **现象**：用户手机上面板点「自检 / 解限流」，弹 `自检请求失败：SyntaxError: Failed to execute
  'json' on 'Response': Unexpec…`。
- **根因（两层，缺一不可）**：
  1. **服务端太慢**：v2.9.20 的自检逐号打 `/api/accounts/<id>/quota` 读 5 小时配额桶，
     那个端点**单次就要 ~3.3s**（它会去上游刷），5 个号串行 ≈16.5s，加探针 3.6s ≈ **20s**。
  2. **面板走 CDN，源站 15 秒超时**：面板域名解析到 EdgeOne（`eo.dnse1.com`）。
     源站超过 15s → CDN 直接返回 **HTTP 524 + 空 body** → 前端 `r.json()` 解析空串
     → 抛裸 `SyntaxError`（就是用户看到的那句）。
- **修法（四条一起上）**：
  1. **配额零额外请求**：5 小时配额桶**直接从 `/api/accounts` 的
     `accounts[].quota.quota_groups[].buckets[]` 里读**，不再逐号打那个慢端点。
     实测两个来源的 `remaining_fraction` 一致（差异只是刷新间隔造成的浮点漂移）。
     只有整个 payload 都读不到 5h 桶时（AM 改版）才回退逐号查，且**并发**。
  2. **池状态与探针并发**：两者互不依赖，耗时取 `max` 而不是相加。
  3. **改异步**：`POST /api/relay-check` 只负责「开跑」并**立刻返回**（实测 140~240ms），
     结果由前端轮询 `GET /api/relay-check` 取；服务端把结果缓存住，
     中途断网再进来也能拿到。连点会去重（不重复打上游）。
     ⚠️ 企微菜单那条路径**不走 CDN**，仍直接同步调 `relay_report()` 出结果。
  4. **前端不再裸 `r.json()`**：先取 `text` 再 `try JSON.parse`，失败就报
     「HTTP 状态 + 返回文本前 120 字」或「返回空 body —— 多半是中间层超时」，
     并显示「已等待 N 秒」。
- 另外把探针 `timeout` 从 90s 收到 25s（上游真挂住时，等 90s 毫无意义）。
- **实测**：源站自检 10/10 稳定 **2.5~3.2s**；从外部干净视角走用户真实路径
  （公网域名 → EdgeOne → 源站）连打 6 次，POST **140~242ms**、整体 **3.8~6.5s**、**6/6 全 200**。
  （v2.9.20 同样路径 3 次里 1 次 524 / 15.26s。）
- 版本串 v2.9.20 → v2.9.21（`/api/meta` 与启动横幅）。

> 💡 **通用教训**：面板域名后面有 CDN 时，**任何源站耗时可能超过 15s 的接口都不能做成同步**。
> 先量「源站耗时」再量「经 CDN 的耗时」，两者之差就是中间层的预算。
> 这里源站明明只有 3s，经隧道抖动却能到 13.6s —— **源站再快也不代表用户端够快**。

**v2.9.20 变化**（2026-09-29）——新增**「中转池」自检 / 解限流**（可选功能，默认关）：

- **解决的问题**：有些中转/反代网关的**限流记录不会自己过期** —— 上游账号配额明明还是满的，
  网关却持续回「全部限流」并报「还要等几小时」，表现为**客户端发消息毫无反应**。
  实测：5 个账号的 5 小时配额桶 `remaining_fraction` 全为 `1.0`（满），网关仍回 `503 all_accounts_limited`；
  清掉限流记录后**立刻**恢复正常。这不是号坏、也不是配额耗尽。
- **自检 + 自愈**：新端点 `POST /api/relay-check`（body 可选 `{"heal": false}` 只看不清）。
  流程 = 读池状态（可用账号数 / 异常标记 / 5 小时配额最低值）→ 打一发探针请求 →
  **只有当探针回「限流」且配额仍高于门槛时**才清限流记录 → 复测确认。
  真实配额耗尽（低于门槛）**不会**误清，只提示「等官方重置」。
- **企微菜单「🔄解限流」**：一级「🔧运维操作」第 5 项（取代原来的 🧹清理临时，
  清理临时改为关键词触发）。点一下先回执「已触发…」，再推一条自检结果。
  也可直接在企微里回复关键词「解限流 / 中转池 / 自愈 / relay」。
- **面板 → 设置 →【中转池】抽屉**：启用开关、管理接口地址、管理员密码、`/v1` 调用密钥、
  探针模型、清锁配额门槛（默认 50%），外加一个「自检 / 解限流」按钮。
  两套凭据**分开配**（管理接口用管理员密码，探针走 `/v1` 用调用密钥，实测互不通用）；
  密码类**只存本机、不回传前端**（前端只回 `*_set` 布尔），留空 = 不修改。
- **修 2 个 hosts 分支的真 bug**：
  · `HOSTS` 动作读错了键（读 `ip`，实际叫 `hosts_ip`）→ **IP 恒显示 `-`**；现在解析失败会单列成
    `· 域名 → 解析失败（DNS 空）`，不再蒙混成正常。
  · `HEALTH` 体检把「解析失败」并进「无需改写」里 → 现在单独统计成 `N 个解析/绑定异常`。
- 版本串 v2.9.19 → v2.9.20（`/api/meta` 与启动横幅）。

**v2.9.13 变化**（2026-09-27）——告警改用 `news` 卡片，微信端也有「可点名字」：

  正文一长链接行就被截没了，而链接恰恰是这条消息唯一能操作的东西。

## 部署（Docker / Docker Compose）

任意装了 Docker 的 Linux 或 NAS 都能跑：纯 Python 无二进制依赖，x86_64 / arm64 均可。

```bash
# 1. 克隆
git clone https://github.com/YisBoss/etkn-monitor.git
cd etkn-monitor

# 2. 准备配置（.env 已被 .gitignore 忽略，绝不会进仓库）
cp .env.example .env
vi .env            # 至少填 ETKN_BASE_URL / ETKN_USERNAME / ETKN_PASSWORD

# 3. 启动
docker compose up -d --build

# 4. 验证
curl http://127.0.0.1:8620/api/meta
```

浏览器打开 `http://<机器IP>:8620`。

> 没有 `.env` 也能启动（`env_file` 是可选项，需要 Docker Compose ≥ 2.24），
> 但连不上 ETKN —— 面板会一直显示取数失败。变量含义见 `.env.example` 和下面「配置」表。

**自动喂料（可选）**：走 **CloudDrive2（CD2）的 WebDAV**，在**面板 → 设置 →【喂料】**里配：
源目录、目标目录、CD2 地址与账号密码（在 CD2 里另建一个只读账号更稳妥）。
保存时面板会**当场连一次 CD2 验证**，不通则整组回滚、不会写入坏配置。
（容器里那个 `/cloud115` 挂载点只是可选占位，与本功能无关：喂料靠 CD2 的 HTTP 接口
在云盘侧直接移动文件，不经过本地挂载。）

**面板地址（可选）**：推给你的消息里「打开面板」链接用哪个地址，按下列优先级自动决定，
**通常不用配**：① 设置项 `trigger_public_base`（显式指定，最优先）；
② **你打开面板时用的地址**（面板会记住，最贴合实际，用域名/反代访问也准）；
③ `MONITOR_LAN_HOST` 环境变量；④ 自探本机出口地址；⑤ `127.0.0.1:端口`。
（之所以不单靠「自探」：面板跑在 Docker 里时自探只能得到网桥地址，对手机不可达。）

**hosts 巡检 / 自动重启（可选）**：需要容器能 SSH 到运行 ETKN 的那台机器，
在 `.env` 里配 `SSH_HOST` / `SSH_PORT` / `SSH_USER` / `SUDO_PASSWORD`。

> 普通用户按上面「部署 / 更新版本」即可，本节只对改代码、发新版的人有意义。

**发版一条命令搞定**（提交 → 推 main → 打 tag → 建 Release → 补齐历史缺失的 Release）：

```bash
python3 scripts/em_release.py v3.19.0 --note "本版改了哪些内容（一两句话）"
# 或把说明写进文件：--note-file CHANGELOG.md
# 只补齐「有 tag 但没 Release」的历史版本：python3 scripts/em_release.py --sync
```

脚本会做两件容易忘的事：

1. **隐私闸门**——推送前扫描全部被跟踪文件与版本说明，命中私人域名、非占位网段的 IP、
   API 密钥、飞书 Webhook、企业微信企业 ID 等即**中止发版**（开源仓库不允许出现部署者的私人信息）。
   通用形态（密钥、Webhook、私网段）内置在脚本里；**你自己的域名/公网 IP 请写进仓库外的
   `~/.hermes/workspace/.creds/em_privacy_denylist.txt`**（每行一条正则）——把私人域名当规则
   写进脚本，脚本进公开仓库就等于泄露它自己。确需跳过检查用 `--skip-privacy`。
2. **Release 补齐**——GitHub 发行版页面只认 **Release 对象**，光 `git push --tags` 不会更新页面。
   脚本每次都会核对「tag ↔ Release」是否一一对应，缺的自动补，避免页面停在旧版本。

凭据从 `~/.hermes/workspace/.creds/github_etkn_monitor.txt` 读取（运行时读，不落盘、不回显）。
需要走代理才能连 GitHub 时，用环境变量指定（默认直连）：

```bash
EM_RELEASE_PROXY=http://192.168.1.1:7890 python3 scripts/em_release.py v3.19.0 --note "…"
```

## 通知渠道

告警支持两条通道，**可以同时开**，任一通道送达即算推送成功；两条通道**各有独立开关**
（面板 → 设置 →【推送】→「飞书通知渠道」/【企业微信】→「企业微信通知渠道」），
另有「推送总开关」作为总闸（关掉则两条都静默）：

| 通道 | 配置位置 | 说明 |
|---|---|---|
| 飞书群机器人 | 面板 → 设置 →【推送】 | 填 Incoming Webhook 地址即可，最省事；卡片带按钮行 + 底部推送时间小字 |
| 企业微信自建应用 | 面板 → 设置 →【企业微信】 | 应用消息（`textcard` 卡片 / 超长回落 `text`）+ 自定义菜单 + 文本指令（回调）；正文带链接行 + 底部推送时间小字 |

面板**页头**会显示 `📣 飞书 · 企微` 徽标（绿=有可用通道 / 红=无可用通道 / 灰=已静默），
悬停看明细；**任务统计页 →「系统状态」**里有「通知渠道」一行，含最近一次企微发送结果。
一眼就能看出「告警到底发不发得出去」。

### 企业微信自建应用接入步骤

1. 企微管理后台 → 应用管理 → 自建 → 创建应用，记下 **AgentId** 与 **Secret**；
2. 应用详情 →「接收消息」→ 设置 API 接收：
   - **URL**：`https://<你的面板公网域名>/wecom/callback`
   - **Token** / **EncodingAESKey**：随机生成后，抄到面板设置里（要一一对应）
3. 「企业可信IP」填**调用企微 API 的出口 IP**——也就是跑本容器那台机器的公网出口 IP。
   出口 IP 会漂（PPPoE / CGNAT）的话，在面板【企业微信】里填「API 代理」，
   把调用固定从某个固定 IP 的机器出去（例：`http://user:pass@1.2.3.4:7897`，
   指向一个只放行 `qyapi.weixin.qq.com:443` 的 CONNECT 代理）；
4. 面板 → 设置 →【企业微信】：填企业ID / AgentId / Secret / 接收人 / 回调 Token / EncodingAESKey
   → 打开开关 → 点「测试企业微信」；
5. 点「下发自定义菜单」，企微客户端里**重新进入应用**即可看到菜单。

菜单结构（v2.9.20）：

```
🔗快捷入口                 ← 二级 = 面板「卡片链接」里配的按钮（view 型，点了直接跳）
  ├ ETKN助手   ├ ETKN   └ CD2      ← 名字/URL/条数都跟着设置走
🔧运维操作                 ← 按「面板上真有的动作 + 常用度」排
  ├ 📁整理一批   ├ ⚡立即测速   ├ 🗂清空登记
  ├ 🩺一键体检   └ 🔄解限流
📚任务中心                 ← 二级 = ETKN 工具箱的 5 个分类
  ├ 🎬媒体维护   ├ 📁115整理   ├ 📺订阅追剧
  ├ 📚媒体库     └ 🔑账号系统
      ↓ 点击分类 → 推一条图文消息（news），每条 = 该分类下一个子任务
      ↓ 点子任务 → 确认页 → 确认执行 → 触发 ETKN
```

> 一级只有 3 个（企微上限），所以「🔄解限流」占用「🔧运维操作」的第 5 个二级位；
> 原来的「🧹清理临时」不常用，改成**关键词触发**（在企微里回「清理临时」即可）。

**「🔧运维操作」的设计逻辑**：只放**面板上真有的动作**（避免菜单和面板两套口径），
按「天天用 → 偶尔用 → 少见」排；凡是「点了只推一条报告」的诊断类，**合并成一个 🩺一键体检**，
一次点出完整结论，而不是让用户连点三次分别看。

> ⚠️ 菜单名受企微限制：**每个名字不超过 16 个字节**（UTF-8；一个汉字 3 字节、一个 emoji 4 字节），
> 超了企微直接返回 `40058` 拒收。改名字前先 `len(name.encode('utf-8'))` 数一遍。
> 面板里改完点「下发自定义菜单」即可，程序会先做本地字节数校验。
>
> ⚠️ 菜单是**下发即固化**的：改代码里的菜单结构后，必须重新点「下发自定义菜单」才会生效
> （企微端也不会主动拉取）。结果回显在设置页「菜单下发结果」一行。
> v2.9.15 起「🔗快捷入口」的 URL 来自 `card_links`，所以**改卡片链接会自动重下发菜单**
> （按指纹判断，没变就不打扰企微）；改其它设置不需要重下发。
>
> ⚠️ 企微自定义菜单**只有两级**（一级 ≤3 个、每个一级下二级 ≤5 个，没有第三级），
> 所以「分类里再展开子任务」菜单做不到，只能靠点击分类后**推一条图文消息**来展开。

### 任务中心（ETKN 原生任务）

面板「任务中心」卡片与企微菜单「📚任务中心」是**同一批任务**（同一份 `TASK_CATALOG`，
面板经 `GET /api/task-catalog` 取用），都走 `POST /api/task-center/tasks/<key>/runs`
（服务端默认参数），触发后任务进入 ETKN 队列，可随时在 ETKN 任务中心取消。

按 ETKN 工具箱的 5 个分类组织，共 26 个任务（每类 ≤8 条，受 `news` 单条 8 篇上限约束）。
出于安全考虑走**白名单**——面板无鉴权，不透传等于给面板开了个「任意任务代理」：

- **破坏性任务一律不收**：`delete-115-shares`（删除分享入库）、`execute-duplicate-media`（执行去重）、
  `apply-auto-tags`（自动打标）、`manually-correct-organize-records`（手动重组记录）等；
- **未实现的不收**：ETKN 里 `implementation_status=planned` 的一律排除；
- 想加减任务，改 `TASK_CATALOG` 一处即可（菜单、面板、白名单都由它派生）。

企微里点分类展开的子任务链接形如
`https://<面板地址>/run-task/<task_key>?token=<进程令牌>`，落地是**确认页**而不是直接触发——
微信/企微打开链接会预取，点开即跑等于打开一条消息就把整类任务全触发。令牌是进程级的
（容器重启即轮换），只防「链接被预取/被猜到」。

### 「中转池」自检 / 解限流（可选功能，v2.9.20 起）

> 默认关闭。不配 = 这个功能完全不出现（菜单点「🔄解限流」只回一句「未启用」）。

**为什么需要它**：部分中转/反代网关的**限流记录不会自己过期**。
上游账号配额明明还是满的，网关却持续回「全部限流」，还报「还要等几小时」，
客户端表现为**发消息毫无反应**（不是号坏、也不是配额耗尽）。

**自检流程**（企微菜单「🔄解限流」与面板按钮**共用这一份实现**）：

1. 读池状态：可用账号数 / 被标记异常的账号 / 各账号「5 小时配额」的最低剩余比例；
2. 用配置的**探针模型**真打一发请求；
3. 若探针回「限流」**且**配额仍高于门槛（默认 50%）→ 清空限流记录 → **复测**确认；
4. 若配额已低于门槛 → 判定为**真实耗尽**，只提示「等官方重置」，**不动**限流记录；
5. 若是别的错误（网络/鉴权等）→ 提示「非限流类错误，未动限流记录」。

报告长这样：

```
🔄 中转池自检
· 账号：4/5 可用，标记异常 1 个
　　xxx@example.com（已禁用）
· 5 小时配额：最低 100%
· 探针 <模型名>：200 ✅ 无需处理
```

**接口（v2.9.21 起是异步的）**：

| 端点 | 方法 | 说明 |
|---|---|---|
| `/api/relay-check` | POST | **只负责开跑，立刻返回** `{running:true, started:true}`（连点返回 `started:false`） |
| `/api/relay-check` | GET | 取任务状态 `{running, ok, lines, elapsed}`；服务端缓存结果，中途断网再进来也能拿到 |

> ⚠️ **为什么必须异步**：面板域名后面是 CDN，**源站超过 15 秒会被换成 HTTP 524 + 空 body**。
> 自检要真打一发模型请求（~3s），经隧道抖动实测可达 13.6s —— 同步做就是踩在悬崖边上。
> 异步之后 POST 实测 140~240ms，客户端永远不碰那个超时。
> 企微菜单那条路径不走 CDN，所以仍直接同步出结果。

**配置项**（面板 → 设置 →【中转池】）：启用开关 / 管理接口地址 / 管理员密码 /
`/v1` 调用密钥 / 探针模型 / 清锁配额门槛。

> ⚠️ **两套凭据是分开的**：读账号与清限流记录走**管理接口**（管理员密码），
> 探针要走 `/v1`（调用密钥）——实测管理员密码打 `/v1` 会被拒（`403 token_rejected`）。
> 密码类字段只存本机、不回传前端；留空 = 不修改。
>
> 💡 **读配额不要用 `/api/accounts/<id>/quota`**：那个端点单次 ~3.3s（会去上游刷）。
> `/api/accounts` 的 `accounts[].quota.quota_groups[].buckets[]` 里**已经有同一份数据**，白拿。
>
> ⚠️ 探针是**真打一发模型请求**，实测约 30 秒（要等上游返回），所以面板按钮会显示「自检中…」；
> 企微菜单会**先回执「已触发…」再推结果**，不用干等。

### 消息格式说明（msgtype 与字节上限）

企微应用消息**不发 `markdown`**——因为**微信端（微信插件）不支持 markdown**，
会显示成「暂不支持此消息类型，请在企业微信中查看」。四种类型的实测对照（真机，只改 msgtype）：

| msgtype | 企业微信 App | 微信 App（微信插件） |
|---|---|---|
| `markdown` | 正常 | ❌「暂不支持此消息类型」 |
| `text` | 正常 | 正常，但**不渲染 markdown**（`**粗体**`、`[名字](url)` 原样露出） |
| `textcard` | 正常（标题 + 描述 + **一个**可点 URL） | 正常（同上） |
| `news` | 正常（标题 + 描述 + 一行行可点名字） | ⚠️ **公众号图文版式**：大图占位 + 标题横幅，**`description` 不显示** |

本程序的选择：

| 用途 | msgtype | 上限（官方口径，UTF-8） |
|---|---|---|
| **告警**（有标题且正文 ≤512 字节） | `textcard`：标题 + 完整正文 + 一个可点 URL | `title` ≤128 字节、`description` ≤512 字节 |
| 告警但正文 >512 字节 / 无标题 | `text`（纯文本；**先给链接行与页脚留位再裁正文**） | `content` ≤2048 字节 |
| **任务中心子任务列表** | `news`（每条一个任务，各带一个可点 URL） | 每条 `title` ≤128 字节；≤8 条 |

都按**字节**裁剪（一个汉字 3 字节），并优先保住末尾的「推送时间」页脚；
正文首行若与卡片标题重复（`⚠️ ETKN 告警 · X` / `✅ ETKN 整理任务已清空…`）会自动去掉。

> ⚠️ **`news` 只能用于「每行自解释」的列表**：部分客户端把它渲染成「公众号图文」，
> `description` 完全不显示、第一条还会占一大块图片位。拿它发告警 = 正文丢失（v2.9.13 踩过）。

> 想在企微 App 里要 markdown 的加粗/标题观感是做得到的，但那样**微信 App 就收不到**——
> 企微没有「按客户端分开发不同 msgtype」的能力，只能二选一。这里选了「两端都能看到」。

### ⚠️ 企业微信 App 收到、但**微信 App** 收不到？

这不是本程序的问题——企微「**微信插件**」是一条独立通道，默认不生效。逐条核对：

1. **微信里先关注「微信插件」**（企微管理后台 → 微信插件 → 生成二维码，用微信扫码关注）；
2. 微信 → 通讯录 → 点已关注的「微信插件」→ 右上角 → 设置 → **开启「接收企业消息」**；
3. 企微管理后台 → 微信插件 → **不要勾选**「成员使用微信插件时需要使用企业微信客户端」；
4. 企微手机端 → 左上角「≡」→ 设置 → 消息通知 → **不要勾选**「仅在企业微信中接收消息」；
5. 应用不能被停用；全员群人数超 2000 不同步到微信插件。

> 官方限制（无法绕过）：若管理端给应用设置了「**在微工作台中始终进入主页**」，
> 应用在**微信端只能收到文本消息，且长度限制 20 字节**，超过会被截断；
> 其他消息类型（含卡片）会被**转成文本**并提示用户到企业微信查看。
> 参考：企微帮助中心《如何接收微信插件消息》与《发送应用消息》文档。

## 安全

- 零密钥设计：密码只放 `.env`（600 权限），不入代码、不入仓库；Git 已忽略 `.env`。
- 测速与重试均为手动触发，无任何定时任务。
- 重试仅转发 ETKN 官方接口；ETKN 的拒绝（409 等）原样透传展示。
- **「中转池」是可选功能，默认关**。开启后管理员密码与 `/v1` 调用密钥只写在**本机配置文件**里，
  `GET /api/settings` 只回 `*_set` 布尔（不回明文），保存时留空即「不修改」。
  本仓库的代码与文档里**不含任何真实地址或凭据**（地址一律用占位符）。
- ⚠️ **面板默认不鉴权**：为方便内网直接使用，出厂状态任何人访问都能**读取并修改全部设置**。
  **请勿把面板直接暴露到公网**；确需公网访问，先在**面板 → 设置 →【面板安全】**里设一个
  **访问口令**（也可用环境变量 `ACCESS_PASS` 在部署时就带上）。设置后浏览器首次打开需输一次口令，
  之后凭 Cookie 免输；推送给你的消息里带的链接会自带一次性令牌，点开无需再输。
- 容器内以 root 运行、并把仓库目录 `./:/app:ro` 只读挂入；面板只监听你映射的端口，
  不做任何出网探测（除你配置的 ETKN / CD2 / 通知渠道地址外）。
